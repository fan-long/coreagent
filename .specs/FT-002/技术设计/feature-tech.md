〔系统特性〕
| id | 特性名称 | 特征 | 识别方法 |
|---|---|---|---|
| 128 | 平台自举迭代 | 平台自身需要演进优化时 | 以平台自身为应用系统，用平台能力完成需求分析→技术设计→代码生成→知识沉淀闭环，闭环产出回灌产品基线 |
| 131 | 需求文档双文档模型（基线Spec与增量Change） | 需求进入平台，需要区分“系统当前是什么”与“本次要改什么”时 | 描述系统当前已具备的能力写基线 Spec（mod）；描述一次跨模块改动写增量 Change（ft）；两者共用同一套编号与验收预期写法 |
| 132 | 能力规格与业务规则的关系（CAP与BR分工） | 编写或评审需求时，需要判断一条内容应写成能力规格还是业务规则 | 能用 GIVEN/WHEN/THEN 表达“条件—动作—结果”的写成能力规格 CAP；只能在任何时刻断言“必须/禁止成立”的写成业务规则 BR；两者都涉及则 CAP 写验收预期并引用 BR 编号 |
| 133 | 需求条目编号体系 | 为模块需求文档中的规则、能力与界面单元分配编号 | 全部编号以模块编号为前缀：BR-<模块编号>-NN、CAP-<模块编号>-NN、UI-<模块编号>-NN，NN 从 01 起递增 |
| 134 | 验收预期写法（GIVEN/WHEN/THEN契约） | 为一条能力编写可验收的预期 | 每条能力至少 1 条正常预期 + 1 条异常预期；预期必须可观察、可判定，能直接转换为测试案例 |
| 135 | 界面需求纳入模块需求 | 需要描述页面、按钮、交互与操作反馈时 | 界面内容不单独成册，作为模块需求文档中的界面规格章节，与能力规格一一对应 |
| 136 | 业务对象与属性描述粒度 | 描述模块负责管理的业务对象与属性时 | 需求阶段不写具体表结构，但属性须细化到可支撑后续表结构设计的程度 |
| 137 | 需求内容边界（以现状实现为准） | 编写模块基线需求时判断哪些内容应当写入 | 只写当前实现已具备的能力；不写待确认问题，不写尚未实现的改进诉求 |
| 138 | 需求文档通用性约束（模板不固化项目信息） | 维护平台中的需求规格模板（mod 模板与 ft 模板）时 | 模板中不得出现任何具体项目的功能域、分组枚举、模块划分与组件标识 |
| 139 | 完备性自检门禁 | 模块需求文档进入下一阶段（技术设计）之前 | 逐项核对文档中的完备性自检清单，全部通过方可进入下一阶段 |
| 140 | 需求来源与追溯 | 记录一条需求的由来、关联范围与后续去向时 | 元信息保留需求来源与涉及组件；关联章节写明上下游模块、关联资产与增量变更去向 |
| 141 | 模块划分与需求组织原则 | 为平台梳理模块化需求、确定模块清单与模块边界时 | 以平台现有功能实现为基线划分模块；一模块一份基线文档；模块按功能分组组织，分组与模块清单由使用方模块字典定义 |
