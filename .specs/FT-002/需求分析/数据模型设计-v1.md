# 数据模型设计

> 组件 core-agent · 模型版本 v1

## 业务领域
- AI AI能力配置(AI Capability)：模型配置、通用 Agent 集成、Skill 配置、Agent 配置、工作流配置
- AS 组件公共资产(Component Assets)：需求文档与需求规则、交易接口设计、数据模型、测试案例、组件/系统特性、补充知识、代码参考
- CV 通用能力(Conversation)：AI 辅助对话、消息留痕与变更提案
- EN 工程实施(Engineering Execution)：工程仓库与工程配置、任务管理与流程执行、问题跟踪
- FM 基础管理(Foundation Management)：全局与项目配置：项目信息、应用组件、应用类型、技术框架、Spec 模板与任务类型

- agent_context Agent上下文配置 主键：agent_id, context_key：Agent 注入上下文字段清单配置
- agent_definition Agent定义 主键：id：平台 Agent 主数据（内置 + 自定义）
- agent_env_config Agent环境变量配置 主键：id：按工具/模型/范围配置 Agent 环境变量

- agent_skill_rel Agent与Skill关联 主键：agent_id, skill_id：Agent 与 Skill 多对多关联，复合主键天然去重

- code_reference 代码参考 主键：id：代码参考主数据，按组件归属
- code_reference_file 代码参考文件 主键：path, ref_id：代码参考下的文件正文与语言、排序
- component_definition 应用组件定义 主键：id：组件主数据，全部组件级资产的归属锚点
- component_repository 组件工程仓库 主键：id：组件下的工程仓库配置，绑定技术框架与任务类型
- component_type 应用类型 主键：id：应用分类字典，用于 Spec 模板组的适配匹配
- db_domain 业务领域信息表 主键：id：按组件存储业务领域清单，数据库设计文档第二章的落地载体
- db_entity 实体（表）信息表 主键：id：按组件存储实体（表）元数据与主键说明、索引建议
- db_info 数据库信息 主键：id：按组件 + 模型版本存储数据库连接与设计文档正文
- interface_doc 交易接口文档 主键：id：交易接口文档元数据，来源需求文档经 requirement_doc_id 关联
- interface_item 交易接口条目 主键：id：交易接口条目（交易码）明细
- issue_tracking 问题跟踪 主键：id：执行过程中的问题记录与 AI 建议、人工补充
- knowledge_item 知识条目明细 主键：item_id, detail_id：知识条目与明细两级结构，可关联代码参考
- model_config 模型配置 主键：model_id：模型接入配置，密钥明文存储待治理
- project_info 项目信息 主键：id：项目主数据，组件的最上层归属
- repository_tasktype_rel 工程仓库与任务类型关联 主键：id：工程仓库与任务类型（含工作流）的关联表
- requirement_doc 需求文档 主键：id：按组件归属的需求文档元数据
- requirement_item 需求条目 主键：id：需求条目明细，AI 提取 + 人工录入，是任务与测试的来源锚点
- requirement_rule 需求规则 主键：id：需求条目下的业务规则明细（本次新增），规则级追溯起点
- requirement_rule_rel 需求规则关联产物 主键：id：需求规则与设计/案例/问题等产物的关联及证据（本次新增）
- skill_component Skill与应用组件关联 主键：skill_id, component：Skill 下发到组件/项目的关联表（无主键，聚簇索引回退 rowid）

- skill_file Skill附属文件 主键：path, skill_id：Skill 附属文件正文
- specgroup_comptype_rel Spec模板组与应用类型关联 主键：id：模板组与应用类型的多对多中间表（value 列由 comptype_value 更名，新增冗余列 type）

- spec_template Spec模板 主键：id：规格组下的阶段化 Spec 模板
- system_feature 系统特性 主键：id：系统特性/规则库特性，可归属组件或项目
- task_instance 任务实例 主键：id：工程执行单元，来源经 requirement_id / interface_id 锚定条目物理主键
- task_type 任务类型 主键：spec_group_id, code：规格组下的任务类型定义，绑定三类 Agent 与可选 Spec 模板
- tech_framework 技术框架 主键：id：框架能力字典，驱动工程仓库的构建/启动与编排、规则库能力开关
- test_case 测试案例 主键：id：测试案例，本次新增 repository_id，与 component_id 构成双归属
- workflow 工作流 主键：id：工作流主数据（run_mode 与 mode 语义重叠待收敛）
- workflow_node 工作流节点 主键：id：阶段下的节点定义，绑定 Agent 与后置处理器

- workflow_script 工作流执行脚本 主键：id：按运行模式生成的工作流执行脚本
- workflow_stage 工作流阶段 主键：id：工作流阶段定义，关联 Agent 分类

## 一、设计约定

### 1.1 命名约定

| 对象 | 规则 | 本模型实例 |
| --- | --- | --- |
| 表名 | 小写 + 下划线，模块前缀，长度 ≤ 32 | component_definition、requirement_rule_rel |
| 字段名 | 小写 + 下划线，避免数据库保留字 | created_at、item_code |
| 主键 | 模板约定统一为 id；本模型为四类主键并存，见第五章 | id、model_id、category、(spec_group_id, code) |
| 唯一索引 | uk_表名_字段 | uk_req_item_comp_code_type_doc、uk_req_rule_rel |
| 普通索引 | idx_表名_字段 | idx_db_entity_domain、idx_req_rule_rel_scope |
| 外键 | fk_主表_从表 | fk_agent_template_agent |

> 本模型未采用模板「主键统一为 id」的约定，改按实体性质选择主键类型，理由与清单见第五章；偏离项已登记于第八章第 2 项。

### 1.2 通用字段约定

- 公共字段：created_at / updated_at（datetime(6) 或 datetime），由应用层写入，无数据库默认值、无 ON UPDATE 触发器；仅 workflow_run、issue_tracking 另有 started_at / finished_at 业务时间（datetime(6)，可空）。requirement_rule 与 requirement_rule_rel 为追加写入的明细表，仅有 created_at，无 updated_at。
- 本模型未采用模板要求的 org_code / created_by / updated_by / deleted_flag / version；数据权限、审计留痕、逻辑删除与乐观锁均由应用层承担，差异登记于第八章第 1 项。test_case.enabled 是本模型唯一的启用标志位，语义为案例是否参与执行，不等同于逻辑删除。
- 未以数据库物理外键作为完整性主手段，全库仅保留 5 条历史外键（见 4.6）。

### 1.3 数据类型约定

| 场景 | 本模型用法 | 与模板差异 |
| --- | --- | --- |
| 布尔 | 多数为 bit(1)；agent_prompt_template.builtin、workflow_script.enabled、agent_definition.auto_bind_skill、test_case.enabled 为 tinyint(1) | 模板推荐统一 tinyint(1)，登记待确认 |
| 枚举 / 字典 | 以 varchar 存编码为主，取值见第六章；本次新增的 requirement_rule.type、requirement_rule_rel.type、requirement_rule_rel.status 使用 tinyint 数值枚举 | 与「枚举用 varchar 存编码」约定不一致，登记待确认 |
| 时间 | datetime / datetime(6)，无时区存储，按 Asia/Shanghai 解读 | 一致 |
| 长文本 | text / mediumtext / longtext | 一致 |
| 金额 | 本模型无金额字段 | 不适用 |

## 二、业务领域概览

模型按组件功能范围划分为 5 个业务领域，作为 db_domain 的初始化清单（领域编码即 db_domain.domain_code，领域内表即 db_entity 记录）。

| 领域编码 | 领域名称 | 英文名 | 覆盖表数 | 领域说明 |
| --- | --- | --- | --- | --- |
| FM | 基础管理 | Foundation Management | 8 | 全局与项目配置：项目信息、应用组件、应用类型、技术框架、Spec 模板与任务类型 |
| AI | AI能力配置 | AI Capability | 15 | 模型配置、通用 Agent 集成、Skill 配置、Agent 配置、工作流配置 |
| AS | 组件公共资产 | Component Assets | 14 | 需求文档与需求规则、交易接口设计、数据模型、测试案例、组件/系统特性、补充知识、代码参考 |
| EN | 工程实施 | Engineering Execution | 5 | 工程仓库与工程配置、任务管理与流程执行、问题跟踪 |
| CV | 通用能力 | Conversation | 3 | AI 辅助对话、消息留痕与变更提案 |

**领域归属原则**：以「资产归属维度」而非「功能入口」划分。组件级资产（需求、接口、数据模型、特性、代码参考、任务、测试案例、需求规则）一律挂在 component_definition 之下；平台级配置（模型、Agent、Skill、工作流）不归属组件，由关联表按需下发到组件。

**标识贯通链路**：project_info.id → component_definition.id → component_repository.id → task_instance.item_code → workflow_run / issue_tracking / test_case，是贯穿 FM→EN 的主干链路；agent_definition.id 贯穿 AI→CV→EN。task_instance 与 test_case 另以 requirement_id / interface_id 反向锚定 requirement_item.id / interface_item.id；本次新增 requirement_rule / requirement_rule_rel，以 requirement_item.id + rule_id 为锚点，向 EN 域的产物（设计、代码、测试案例、问题）提供规则级追溯。

### 4.1 基础管理（FM）

项目主数据，组件的最上层归属。

| 字段 | 类型 | 键 | 说明 |

| id | bigint | PK, AUTO | 项目ID |
| name | varchar(128) | NOT NULL | 项目名称 |

| scope | text | | 项目范围 |

## 五、主键策略

模型采用四类主键并存的策略，选择依据为「该实体是自然业务对象、配置项还是关系 / 明细」。本次表结构变更未涉及主键调整，四类主键归属与上一版本一致（新增两张表均采用自增代理键）。

### 5.1 自增代理键（bigint AUTO_INCREMENT）

**约定**：自增主键仅用于物理定位与关联引用，不作为业务语义载体；对外暴露一律使用业务编码（item_code、target_id 等）。无稳定自然键、以记录为单位的实体与流水表归入此类。

> 待核对：本节清单以 DDL 为准，实际为 project_info、component_type、spec_group_definition、specgroup_comptype_rel、spec_template、agent_prompt_template、agent_env_config、requirement_item、requirement_rule、requirement_rule_rel、interface_item、test_case、system_feature、task_instance、workflow_run、workflow_script、issue_tracking、ai_conversation、ai_message、change_proposal、repository_tasktype_rel 共 21 张（本次新增 requirement_rule、requirement_rule_rel）；db_info 的 id 虽为 96 位字符串，但语义上等同代理键。清单口径需统一（第八章第 22 项）。

### 5.2 业务字符串主键（varchar）

适用于跨系统 / 跨模块引用、需要可读且稳定的配置型实体：

| 表 | 主键 | 长度 | 语义 |
| --- | --- | --- | --- |
| component_definition | id | 32 | 应用组件标识，全平台资产归属锚点 |
| tech_framework | id | 32 | 技术框架标识 |
| model_config | model_id | 32 | 模型标识 |
| agent_category | category | 32 | Agent 分类名称（自然键） |
| agent_integration | tool | 32 | 工具名称（自然键） |
| agent_definition | id | 64 | Agent 标识 |
| skill_definition | id | 16 | Skill 标识 |
| workflow / workflow_stage / workflow_node | id | 64 | 工作流 / 阶段 / 节点标识 |
| component_repository | id | 64 | 工程仓库标识 |
| requirement_doc / interface_doc | id | 64 | 文档标识 |
| db_info | id | 96 | 数据库信息标识（{组件id}:{版本} 派生） |
| code_reference | id | 32 | 代码参考标识 |
| knowledge_item | item_id | 32 | 知识条目标识（复合主键前半） |

**约定**：业务主键一旦生成不可变更；组件标识变更时，其下所有以 component_id 为归属的资产需按边界说明同步迁移。

### 5.3 复合主键（关系表与明细表）

| 表 | 复合主键 | 设计意图 |
| --- | --- | --- |
| task_type | (spec_group_id, code) | 任务类型编码仅在规格组内唯一，必须携带组维度 |
| agent_context | (agent_id, context_key) | 一个 Agent 下上下文项唯一 |
| agent_skill_rel | (agent_id, skill_id) | 天然多对多，复合主键即去重约束 |
| skill_file | (path, skill_id) | 相对路径在 Skill 内唯一 |
| code_reference_file | (path, ref_id) | 相对路径在代码参考内唯一 |
| knowledge_item | (item_id, detail_id) | 知识条目 + 明细两级结构 |

**约定**：纯关系表一律用复合主键，不用自增 id，避免重复关联；明细表用「父键 + 子自然键」保证父内唯一。skill_component、repository_tasktype_rel、specgroup_comptype_rel、requirement_rule_rel 当前采用「自增 id + 唯一键」的写法，与本节约定不一致，建议统一收敛（第七章第 15 项、第八章第 20、30 项）。

### 5.4 语义派生主键

仅用于数据模型域的 db_domain 与 db_entity：

- db_domain.id = {组件id}:{域编码}，如 deposit:RB
- db_entity.id = {组件id}:{表名}，如 deposit:RB_BASE_ACCT

设计意图：使域与实体在跨组件范围内全局唯一且人类可读，便于 AI 提案按此 id 精确定位对象。代价是组件标识变更时需级联重写全部 id 与其引用，属已知取舍（第八章第 12 项）。

### 5.5 主键选用规则小结

1. 有稳定自然键的配置型实体 → 业务字符串主键；
2. 无自然键或高频写入的实体 / 流水 → 自增代理键 + 业务唯一键；
3. 关系表 → 复合主键；明细表 → 父键 + 子自然键；
4. 需要跨组件全局可读定位的设计对象 → {组件id}:{业务键} 语义派生主键。

> 新增引用提示：task_instance.requirement_id / interface_id 与 test_case.requirement_id 直接引用上述第 2 类的自增物理主键，requirement_rule / requirement_rule_rel 的全部关联亦建立在 requirement_item.id 这一自增物理主键之上，属于对「对外一律使用业务编码」约定的例外，已在第八章第 24 项登记。

## 九、边界说明

- 能力边界：本模型仅覆盖平台自身 5 个分组 27 个模块已实现的能力；行业与企业差异通过功能与技术配置适配，不在平台内做行业定制；功能权限与操作审计、制品版本与基线、运行事件与可观测等尚未实现的能力不在当前范围。
- 依赖边界：平台不内置模型与命令行 Agent，执行能力由外部工具提供并经 agent_integration 接入，平台只负责上下文组装、调用编排与结果落库。
- 人机边界：AI 产出均为候选方案，需求基线、配置与资产变更须经人工确认后生效（体现为 change_proposal 的确认与 db_domain / db_entity 的 last_proposal_id 回指）；requirement_rule_rel 的 status=1（已确认）是该边界在规则级追溯上的体现。
- 资产边界：组件是工程仓库、需求文档、接口文档、数据域、数据实体、组件特性、代码参考、任务实例等组件级资产的唯一归属维度；当前标识变更仅同步迁移工程仓库、删除组件仅校验工程仓库数量，其余资产的同步迁移与删除校验尚未实现。test_case 于上一版新增 component_id、本次新增 repository_id，requirement_rule / requirement_rule_rel 经 requirement_item 间接归属组件，其是否纳入组件标识同步迁移范围需一并确认。
- 数据承载边界：平台不承载具体应用系统的业务逻辑与业务数据，db_info / db_domain / db_entity 仅存储设计元数据与设计文档正文；requirement_rule 存储的是需求规则的文本内容，属工程资产而非业务数据。
