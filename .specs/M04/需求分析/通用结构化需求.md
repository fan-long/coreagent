# M04 应用类型 —— 结构化需求规格

> 本规格依据《通用结构化需求》模板编制，将 M04 模块的 OpenSpec 能力基线（原始需求）与数据模型设计转换为统一、可追踪、可验证的需求规格。
>
> 需求条款（RC）是统一追踪单元；共享定义（DEF）提供语义；能力（CAP）组织条款；验收检查点（AC）定义验证义务。
>
> 本规格不替代技术设计、实施任务或测试报告，也不因填写完成而证明实现正确。
>
> 条款编号采用统一追踪编号 RC-M04-01…RC-M04-33；「来源」列同时标注源文档的原始编号（BR-M04-xx / CAP-M04-0x / UI-M04-0x），以便与源文档互查。能力编号沿用源文档 CAP-M04-01…CAP-M04-06，检查点编号 AC-M04-01…AC-M04-40，待决事项编号 Q-M04-01…Q-M04-13。
>
> 测试案例说明：本阶段输入为「任务类型 mod 任务项 M04 下无未禁用（启用）测试案例」，即 M04 无既有可用测试案例，故本阶段测试案例清单全部为新增案例（无复用、修改与删除项）。

### 1.2 目标与边界

- **业务目标**：以最少的维护成本维护应用组件特征维度，并让 Spec 组能够按类型值精确圈定适用范围；应用类型字典是规格匹配的公共词汇表（SRC-001 §1.2）。
- **成功标准**：同一类型下不出现重复类型值；新增类型无需单独建维度记录；删除类型后其取值不再出现在列表中（SRC-001 §1.2）。
- **建设对象**：core-agent 平台 M04 模块范围内的「环境管理 / 模板管理 / 应用类型」页（左侧类型列表、右侧类型值表格、新增类型值页、删除类型入口），以及应用类型值的新增、列表读取、编辑、删除单条与删除整个类型的处理。
- **纳入范围**：
  - 应用类型值的列表读取与「类型—类型值」主从视图展示；
  - 类型与类型值的必填、空白裁剪、长度上限与同类型下唯一性校验；
  - 新增类型值时由类型名称自动形成新维度的处理；
  - 删除单条类型值与删除整个类型（含其全部取值）；
  - 类型列表的取值数量聚合与页脚统计；
  - 应用类型值作为 Spec 组适用范围勾选对象的取值供给。
- **排除范围**：
  - 不维护应用组件实例与类型值的绑定关系（对应 M03 应用组件，SRC-001 §1.3）；
  - 不维护 Spec 组与阶段模板（对应 M06 Spec模板与任务类型，SRC-001 §1.3）；
  - 不定义类型值的级联校验与引用完整性约束（SRC-001 §1.3）；
  - 不提供功能权限与操作审计（平台尚未具备该能力，SRC-002 §9 边界说明）；
  - 不定义类型维度的独立实体、排序号维护入口与维度重命名操作（来源未规定，见 Q-M04-03、Q-M04-05）；
  - 不承载需求规则链路与测试案例归属等 SRC-002 §8 第 27、29、30、31 项所列问题（属 AS 域需求规则与测试案例范围，与本模块无关）；
  - 跨模块的增量变更以功能点（ft）方式另行登记，不在本规格范围。
- **外部责任**：
  - Spec 组与类型值的关联关系的维护（勾选、保存、全量替换）由 M06 Spec模板与任务类型承担，M04 只提供可选值集合（SRC-001 §1.3、§5 CAP-M04-06 范围边界）；
  - Spec 编辑界面中已关联类型值的徽标展示与未关联文案的呈现由 M06 页面承担（SRC-001 §5 CAP-M04-06 验收预期第2、3条，责任归属待 Q-M04-04 澄清）；
  - 关联行的存储结构（含冗余列 type 的写入与同步）由数据模型设计与 M06 承担，M04 不写入 specgroup_comptype_rel（SRC-002 §4.1 specgroup_comptype_rel、§8 第 28 项）；
  - 应用组件特征描述口径的消费由 M03 应用组件承担（SRC-001 §8）；
  - 平台字典数据的持久化载体与索引由数据模型设计承担（SRC-002 §4.1 component_type）。

按实际内容展开：

- **对象（DEF-M04-01 应用类型值）**：标识方式为自增主键 id（SRC-002 §5.1 自增代理键，「对外暴露一律使用业务编码」的约定在本表不适用，因本表无业务编码列）；归属范围为平台级，不归属组件；相关对象为下游的 specgroup_comptype_rel（经 value 列逻辑引用，类型维度另由该表的冗余列 type 承载，DEF-M04-12）。
- **概念（DEF-M04-02 类型）**：类型不是独立实体，没有独立的类型记录、类型标识与类型级属性；类型的存在性由「字典中是否至少存在一条该类型的取值记录」决定（RC-M04-10 的判定基础）；类型的展示顺序由该类型下取值记录的排序号推导（RC-M04-06），排序号的维护入口与取值规则未在来源中规定（见 Q-M04-05）。
- **属性（DEF-M04-03、DEF-M04-04）**：均为文本；空值含义上，类型值为必填（空值不允许），值说明为空表示「无说明」并按空字符串存储，不表示禁用或不适用；长度上限见 SRC-001 §1.4 与 SRC-002 表结构，超限处理未在来源中规定，见 Q-M04-09。
- **属性（DEF-M04-05 排序号）**：为可空整数；升序展示；「预置维度按预设分类顺序展示」中的预设顺序未在来源中给出，见 Q-M04-05、Q-M04-06；新增类型的排序号取值、同排序号时的第二排序键（ID 升序）已在 RC-M04-06 明确。
- **关系（DEF-M04-08 Spec 组关联）**：关联由 M06 页面按勾选结果以全量替换方式维护；本模块不校验关联、不清理关联（RC-M04-12）；关联行的存储列为 (group_id, value, type)，其中 type 为可空冗余列且同步规则未定义（DEF-M04-12），value 又可跨类型重复，故「仅 value」与「type + value」两种粒度口径的匹配问题见 Q-M04-01。
- **统计 / 派生数据（DEF-M04-10）**：取值数量为左侧类型列表每项的展示值，类型总数与取值总数为页脚「N个类型 · M条取值」的展示值；三者均由字典基础数据派生，不单独存储（RC-M04-15）。
- **枚举（DEF-M04-09 预置维度）**：来源仅给出规模口径（9 个维度、37 个类型值）与部分维度名称，未给出完整清单与预设分类顺序，见 Q-M04-06；预置数据可被编辑或删除，不属于锁定数据。

## 3. 可验证需求条款

### 3.1 条款定义

需求条款是在明确的适用范围和条件下，对目标系统提出的一项可独立判断是否满足的要求。一条条款可以包含同一决策的多个分支，分支以「分支a / 分支b」标注并可分别验证。能够分别违反、分别修改的要求已尽可能拆分。

### 3.2 条款类型

| 类型 | 表达内容 | 重点检查 |
|---|---|---|
| 业务规则 | 许可、禁止、决策、计算及业务不变量 | 条件、结论、计算口径、例外及优先级 |
| 功能行为 | 必须执行的动作、状态变化和业务效果 | 触发、动作、完成条件、成功及失败结果 |
| 数据要求 | 数据结构、含义、关系、记录与保留要求 | 对象范围、数据契约、关联及有效性 |
| 交互契约 | 人机或系统间的信息交换与协作 | 输入、输出、错误、关联标识及交互时序 |
| 质量约束 | 规定条件下的质量指标与保障要求 | 环境、负载、指标、阈值及测量口径 |

每条条款选择一个主类型登记。本规格不登记质量约束类条款：来源未给出可测量的质量指标（环境、负载、统计窗口、阈值），§1.2 的三项成功标准均为可判定的功能结果，已分别由 RC-M04-04、RC-M04-05、RC-M04-08 与 RC-M04-26 承载，不编造阈值。

### 6.2 验证形式说明

- **场景验证**：给定具体条件、操作或事件，检查预期结果，适合正常、异常、边界和状态分支。本规格多数检查点采用此形式。
- **性质验证**：在明确输入域、状态域或操作序列中检查应持续成立的关系。本规格未单独采用：来源未给出可枚举的输入域或操作序列不变量（RC-M04-04 的同类型下唯一性已通过 AC-M04-06/07/08 以具体场景验证，避免引入原需求未规定的不变量）。
- **测量验证**：在规定环境、负载和时间窗口中测量指标。本规格未采用：来源未给出可测量的质量指标（见 3.2）。
- **静态契约检查**：检查结构、声明、接口或其他可静态判定的约束。本规格用于对象结构（AC-M04-19、AC-M04-20）、页面结构（AC-M04-30、AC-M04-33、AC-M04-34、AC-M04-35、AC-M04-36）与预置顺序（AC-M04-11）。

未为使用性质测试而增加原需求没有规定的不变量、幂等或可逆性要求。

本次为首次建立后的口径同步修订（规格版本仍记为 v1.0）：SRC-002 由 43 张表更新为 45 张表，其中 `specgroup_comptype_rel` 的应用类型值列由 `comptype_value` 更名为 `value`，并新增可空冗余列 `type`。据此同步调整的内容为：DEF-M04-12（关联行结构）、AC-M04-17 / AC-M04-30 / AC-M04-39（关联行的观察入口）、Q-M04-01（由冲突/阻断下调为歧义/非阻断）、Q-M04-13（补入 §7 第 15 项的列更名影响与 §8 第 28 项）与 1.3 / 1.4 / 7.2 的相关表述。条款清单（RC-M04-01…RC-M04-33）的数量、编号与规范性要求均未变化，故不构成 RC 级差异。

后续变更处理约定：

- 同一要求的修订保留 RC 标识并更新规格版本；
- 拆分、合并时记录旧条目与新条目的对应关系，不丢失来源和历史；
- 共享定义（DEF）或适用范围变化时，即使条款正文未改动，也须评估引用它们的条款（如 DEF-M04-02 类型定义变化将影响 RC-M04-05、RC-M04-08、RC-M04-10、RC-M04-14 及其检查点；DEF-M04-11 表结构变化将影响 RC-M04-04、RC-M04-14、RC-M04-19；DEF-M04-12 关联行结构或冗余列 type 的同步规则变化将影响 RC-M04-12、RC-M04-27、RC-M04-28 及其检查点 AC-M04-17、AC-M04-30、AC-M04-39）；
- 本模块为现状基线，源文档 §1.1 所述现状（类型不是独立实体、删除不联动清理关联、类型值按 value 单列被下游引用且类型维度由冗余列承载）属现状观察；后续如引入独立类型实体、维度重命名操作或引用完整性校验，须按变更方式更新本规格并重新评估 Q-M04-01、Q-M04-03、Q-M04-07；
- 规格生效、实施完成和验证通过分别由对应流程及证据判定，不由本规格自行认定；
- 跨模块的增量变更（如类型值对 M06 的取值供给方式调整、关联存储粒度由 Q-M04-01 裁决后的方案落地、M03 组件特征描述口径调整）以功能点（ft）的 Change 方式另行登记，不直接改写本基线。
