## 2. 总体实现方案

### 2.1 技术结构与边界

**系统入口与构件分工**

```
[浏览器]
  #/env/app-type ──> router.js（已有路由常量 nav-config.ENV_NAV_GROUPS）
                     └─ main.js mountView('env') ──> D-M04-12/C-01 分派
                          └─ D-M04-08 应用类型页（主从视图 + 新增界面 + 删除类型确认）
                               │  取数/提交（http.js，D-M04-12/C-02 新增 del）
                               ▼
[core-agent 服务端]
  D-M04-01 读取接口 GET  /api/app-types              ─┐
  D-M04-02 新增接口 POST /api/app-types/values        │
  D-M04-03 编辑接口 PUT  /api/app-types/values/{id}   ├─> D-M04-06 字段规则（纯函数）
  D-M04-04 删除接口 DELETE /api/app-types/values/{id} │    D-M04-07 排序与聚合口径
  D-M04-05 删除类型 DELETE /api/app-types?type=X     ─┘         │
                               │                                │
                               ▼                                ▼
                        D-M04-11 数据访问（ComponentType 实体 + 仓储）
                               │
                               ▼
                   MySQL  component_type（外部 DDL 维护，唯一键 (type, value)）

  D-M04-10 错误码与提示文案（ErrorCode / BizException / GlobalExceptionHandler → ApiError）
  D-M04-14 常量与预置维度（长度上限、页面文案、预置维度清单）
  D-M04-13 跨单元协作（页面 ↔ 接口 ↔ 数据 ↔ 文案，以及向 M06 的取值供给）
```

**数据流动**

- 读取：页面挂载或任何写操作成功后，调用 `GET /api/app-types` 一次取回分组字典（D-M04-01）；服务端单次有序读取 `component_type` 全表（D-M04-11/C-02），按 `(sort_order, id)` 升序在内存中按 `type` 分组（D-M04-01/P-04），装配为「类型列表（含取值数量）+ 各类型取值明细 + 页脚统计」的树形响应。左侧选中切换、右侧表格渲染、页脚统计均来自同一次响应（DD-M04-02），前端不再逐类型取数。
- 写入：新增/编辑/删除均以单条 HTTP 请求提交（D-M04-02…D-M04-05），服务端在同一事务内完成校验、写入/删除与响应装配；页面在成功后**重新调用读取接口**刷新主从视图（不依赖响应体做增量拼接，避免本地字典与服务端不一致，D-M04-08/C-15）。
- 供给侧：M06 Spec 模板页的取值供给复用同一读取契约（D-M04-09），本模块不新增第二个取数端点，使「勾选对象集合」与「应用类型页展示的字典」永远同源同序（DD-M04-02）。
- 同步、异步、批量及调度边界：本模块**全部为同步的人机交互请求**，无异步受理、无批量提交、无定时调度（需求 §6.2 已确认无状态字段与异步特征）。删除整个类型是**同一请求内的一次批量删除**（D-M04-05/P-03），对外语义仍为一次同步操作，不引入批次与进度语义。

**本系统、外部系统与人工活动的责任分工**

| 活动 | 责任主体 | 本设计中的体现 |
|---|---|---|
| 字典的维护（增、改、删、查） | 本系统（M04） | D-M04-01…D-M04-08 |
| Spec 组与类型值关联关系的维护（勾选、保存、全量替换） | 外部（M06 Spec模板与任务类型） | 需求 1.2 外部责任；本设计只提供取值集合（D-M04-09/C-05） |
| 关联行的存储、冗余列 `type` 的写入与同步、历史数据回填 | 外部（数据模型设计与 M06） | 本模块不写入 `specgroup_comptype_rel`（D-M04-11/C-09，结构性保证） |
| 已关联徽标与「未关联应用类型值」文案的呈现 | 外部（M06 页面，责任主体待 Q-M04-04 澄清） | 范围外，RC-M04-28/29 不实施（见 1.1 排除范围） |
| 应用组件与类型值的绑定、组件特征描述口径的消费 | 外部（M03 应用组件） | 范围外 |
| 表结构的建立与预置数据的存在性 | 外部（数据模型设计/部署 DDL） | 本设计不新增列、索引、唯一键（DQ-M04-15） |
| 字典数据的日常维护决策（新增哪个维度、删除是否妥当） | 人工（项目架构师） | 本设计只提供界面与校验，不做业务判断，不引入审批或权限 |

## 4. 设计单元详细规格

### D-M04-01 应用类型字典读取接口

#### 4.1 责任与边界

- 设计职责：提供一次取回「按类型聚合的字典」的读取契约，装配左侧类型列表（含每类型取值数量）、右侧取值明细与页脚统计（类型总数、取值总数），并保证三者来自同一次取数与同一排序口径。
- 调用者或使用方：D-M04-08 应用类型页（挂载、写操作成功后刷新、失败重试）；D-M04-09 取值供给契约（M06 消费）。
- 依赖：D-M04-11（有序读取全表）、D-M04-07（分组、排序、统计口径）、D-M04-10（失败错误码）、D-M04-14（页面文案常量不参与本接口）。
- 技术依据：DD-M04-02（全量分组读取）、DD-M04-04（排序口径）、DD-M04-12（平台级字典，不要求 `X-Project-Id`）、DD-M04-11（类型不是实体）。
- 不承担的责任：不做分页、筛选、关键字检索与增量同步（需求未规定）；不做服务端缓存与预取（会破坏 RC-M04-13 要求的「按当前取值行实时统计」）；不写入任何数据；不提供类型实体的读取（无类型实体）；不提供排序号维护入口。

#### 4.4 状态、数据与失败处理

- 读取的数据：`component_type` 的全部行（`id`、`type`、`value`、`description`、`sort_order`）；不读取任何其它表。
- 写入条件与事务边界：无写入；整方法标注 `@Transactional(readOnly = true)`。
- 并发冲突：本接口为只读，不产生冲突；与并发写请求的可见性见 C-08，不引入锁与版本号。
- 重复请求的识别与响应：读取为幂等操作，重复请求返回同一状态下的同一结果，不需要去重标识。
- 超时、中断、部分失败后的状态：HTTP 请求超时由前端 `http.js` 以 10 秒计时并以 `TIMEOUT` 错误提示（D-M04-12）；服务端无中间状态需恢复；不存在部分失败。
- 资源占用与释放：无长连接、无游标、无文件句柄；结果集规模由字典规模决定（见 DQ-M04-17）。
- 错误分类与传播边界：仅一类失败——数据访问层异常，统一映射为 `M01-E006`（503），不向调用方泄露 SQL 或表名；不上抛为 `M01-E006` 之外的码位，以免前端错误处理分支增加。

#### 4.5 质量与可验证性

- 安全：接口只读，无越权写入风险；响应不含敏感信息（字典为平台级公共词汇表，无凭据与个人信息）；不暴露数据库结构（异常消息统一为固定文案）。
- 性能与容量：单次全表有序读取 + 内存分组，规模为现状 9 类型/37 取值，读取代价可忽略；无分页与缓存，规模化上限与后续演进见 DQ-M04-17。未使用需求未要求的索引（`sort_order` 上的排序为内存外的数据库排序，表规模小，不新增索引，见 DQ-M04-15）。
- 可用性：读取失败不导致白屏（前端失败块 + 重试），失败提示与空态互斥（RC-M04-19）。
- 日志与诊断：`service` 层以 `log.debug` 记录读取到的行数与分组数（不记录全量数据），失败由 `GlobalExceptionHandler` 记录异常与 `traceId`；日志不含敏感信息（本模块无敏感字段），且不输出完整字典内容以避免噪声。
- 验收可观察点：HTTP 状态、响应 JSON 的 `types`/`typeCount`/`valueCount`/各类型 `valueCount` 与顺序、以及页面渲染结果；对应 V-M04-10、V-M04-18、V-M04-21、V-M04-40。
- 受控验证支持：排序断言可通过构造非连续排序号与同排序号数据受控触发（AC-M04-10）；预置维度顺序断言依赖预置清单（待补充，见 V-M04-11）。

#### 4.4 状态、数据与失败处理

- 写入的数据：`component_type` 一行（`type`、`value`、`description`、`sort_order`）；`id` 由自增主键生成。不写其它表（DD-M04-07）。
- 事务边界：`AppTypeService#create` 标注 `@Transactional`；校验、唯一性判定、`MAX(sort_order)` 读取与 `INSERT` 在同一事务内；方法返回即提交，响应中的 `id` 与 `sortOrder` 为已提交状态。
- 提交后可观察结果：重新调用 D-M04-01 读取接口，新记录出现在其类型的取值明细末尾（`sort_order` 为最大值），该类型 `valueCount` 与全局 `valueCount` 各 +1（AC-M04-25）。
- 并发冲突的检测与处理：两个并发新增提交相同 `(type, value)` 时，可能同时通过 P-05 的应用层判定；此时库级唯一键拒绝后写入者，`DataIntegrityViolationException` 被捕获并映射为 `M04-E006`（与先写成功的请求返回同一文案），对外表现为「一次成功、一次重复拒绝」，不产生重复数据（DD-M04-06）。两个并发新增不同取值时，`MAX(sort_order)` 可能取到同一值，产生同排序号的记录——按 C-03 的次级排序键（记录 ID 升序）顺序仍然确定，不视为故障。
- 重复请求的识别与响应：需求未要求幂等键（RC-M04-14 无版本字段与幂等要求），本设计**不引入**去重机制；重复提交同一内容时第二次因唯一性判定被拒绝（`M04-E006`），行为与「重复数据被拒绝」一致，具有自然的防重效果。
- 超时、中断、部分失败后的状态：请求在事务提交前中断则无写入；提交后响应中断（网络失败）时数据库已写入，用户重试将收到 `M04-E006` 重复提示——该情形不改写数据且失败可观察，不引入补偿（模板要求不得默认增加补偿）。
- 资源占用与释放：无外部资源；连接由 Spring 事务管理释放。
- 错误分类与传播边界：业务校验失败 → `BizException` + M04 码位；数据访问异常 → `M01-E006`（503）；请求绑定失败 → 平台既有 `M01-E001`（400）。前端统一以 `message` 提示，不需要区分码位即可展示原因（码位用于验证断言与差异化处理）。

#### 4.5 质量与可验证性

- 安全：无权限校验（平台当前无权限能力，需求 1.2 排除范围）；输入经裁剪与长度限制，且写入使用参数化 JPA 操作，无注入风险；错误消息不回显 SQL 与堆栈。
- 性能与容量：单次 `exists` + `MAX` + `INSERT`，索引使用既有唯一键 `(type, value)`（`exists` 判定走该唯一键）；写入路径无锁定读，规模相关的耗时不影响交互。
- 日志与诊断：`log.debug` 记录创建结果的 `id` 与类型名（类型名属于业务数据但不敏感）；不记录完整请求体以外的额外信息；失败由统一异常处理记录 `traceId`。

- 受控验证支持：超限（64/65）与判重（同类型重复、跨类型同名）均可用构造数据受控触发；库级唯一键冲突分支（P-07 的捕获）需以「绕过应用层判重」的构造手段触发，验证方法见 V-M04-42。

#### 4.6 复用核对

- 影响范围：无（新增类，不影响既有调用方）。

#### 4.4 状态、数据与失败处理

- 写入的数据：删除 `component_type` 一行，不修改任何其它行。

- 重复请求的识别与响应：重复删除第二次通常得到 `M04-E007`（记录已不存在），与 RC-M04-09 的提示要求一致，不额外引入幂等键。
- 超时、中断、部分失败后的状态：事务未提交则无变化；提交后响应中断时该行已删除，用户重试将得到 `M04-E007`——失败可观察，不引入补偿。

### D-M04-05 应用类型整体删除接口

#### 4.1 责任与边界

- 设计职责：按类型名批量删除该类型下的全部取值记录，判定「未指定类型」（`M04-E009`）与「类型不存在」（`M04-E008`），返回删除条数以支撑成功提示文案中的 N。
- 调用者或使用方：D-M04-08 右侧详情标题行的「删除类型」按钮（经确认弹窗后提交）。
- 依赖：D-M04-06/C-09（类型名归一与未指定判定）、D-M04-11（`countByType`、`deleteByType`）、D-M04-07/C-03（类型存在性判定口径）、D-M04-10（`M04-E008`/`M04-E009`）、DD-M04-03（查询参数传递类型名）。
- 技术依据：DD-M04-11（不删除类型实体）、DD-M04-07（不校验、不清理关联）、DD-M04-03。
- 不承担的责任：不删除类型实体（不存在类型实体）；不做关联校验、级联清理与提示（RC-M04-12）；不做二次确认（界面侧，见 D-M04-08/C-23）；不提供按其它条件批量删除的能力。

#### 4.2 契约与结构

| 契约项标识 | 名称或操作 | 输入/结构 | 输出/约束 | 错误或边界 |
|---|---|---|---|---|
| C-01 | `DELETE /api/app-types?type=X` 删除整个类型 | 查询参数 `type`（类型名称文本，由前端 `withQuery` 编码）；无请求体 | `200` + `{"type":"行业领域","deletedCount":5}` | 不接收请求体；忽略其它未知查询参数 |
| C-02 | 类型名归一与未指定判定 | 参数经 D-M04-06/C-09 归一：`null`、空串、仅空白字符一律归一为空并判定为「未指定」 | 非空则进入 C-03 | 未指定 → `M04-E009`（400「请指定类型」） |
| C-03 | 类型存在性判定 | 以归一后的类型名调用 D-M04-11/C-04 `countByType(type)` | `count > 0` 视为类型存在（DEF-M04-02：类型存在性由其取值记录决定） | `count == 0` → `M04-E008`（404「类型不存在：X」，X=归一后的请求携带类型名） |
| C-04 | 删除范围 | 删除该类型下的**全部**取值记录（一次批量删除，RC-M04-08） | `deletedCount` = 被删除的行数，等于 C-03 得到的 `count`；其它类型的记录不受影响 | 不删除任何类型级数据（无类型表） |
| C-05 | 与 Spec 组关联的关系 | 不查询、不写入 `specgroup_comptype_rel` | 关联记录保持原状（RC-M04-12）；被删取值在关联表中形成悬空行，其展示口径属 M06（Q-M04-07，范围外） | 无「被关联不可删除」类拒绝分支（结构性保证） |
| C-06 | 成功提示所需信息 | 响应中的 `type` 与 `deletedCount` | 前端据此组装 `类型「X」及其 N 条取值已删除`（DEF-M04-13/14：X 为类型名、N 为删除前该类型取值条数） | N 必须与删除前该类型取值条数一致（AC-M04-13、AC-M04-38） |
| C-07 | 错误契约汇总 | — | `M04-E008`（404）、`M04-E009`（400）、`M01-E006`（503） | 统一 `ApiError` 响应体；不产生 `M01-E001`（无请求体绑定） |
| C-08 | 副作用 | 一次批量 `DELETE` | 无关联表写入、无审计写入、无级联 | 失败整体回滚，不产生部分删除 |

#### 4.3 处理逻辑

| 处理项标识 | 条件或触发 | 技术处理 | 状态/数据/外部效果 | 后续或结束 |
|---|---|---|---|---|
| P-01 | 收到 `DELETE /api/app-types?type=X` | 读取查询参数并归一（D-M04-06/C-09）；归一后为空 → 抛 `BizException(M04_E009)` | 无写入 | 非空 → P-02 |
| P-02 | 类型存在性判定 | `long n = countByType(type)`；`n == 0` → 抛 `BizException(M04_E008, "类型不存在：" + type)` | 无写入 | `n > 0` → P-03 |
| P-03 | 删除 | `deleteByType(type)`（`@Modifying @Query("delete from ComponentType c where c.type = :type")`，返回受影响行数；或使用派生删除方法返回计数） | 批量 `DELETE`，影响 `n` 行 | P-04 |
| P-04 | 响应 | `200` + `{"type": type, "deletedCount": n}` | 事务提交后该类型下全部取值对外不可见，类型从类型列表消失 | 结束（`200`）；页面提示成功并刷新（D-M04-08/C-24、AC-M04-13） |
| P-05 | P-01/P-02 拒绝 | 抛出对应 `BizException`，事务内无写入 | 数据库无变化 | 结束（400/404） |

- 优先关系（对应需求第 5 节「优先于」）：未指定（P-01）优先于类型不存在（P-02），类型不存在（P-02）优先于删除（P-03）。对应 RC-M04-11、RC-M04-10 分别优先于 RC-M04-08。当请求既未指定类型又无法判定存在性时，返回 `M04-E009`（400）。
- 计数与删除的一致性：`n` 取自 P-02 的计数并在同一事务内用于 P-03 与 P-04，保证响应 `deletedCount` 与删除前计数一致；若并发新增同一类型的取值，可能使实际删除行数大于 `n`——此时以 **P-02 的计数** 作为 `deletedCount` 会让提示中的 N 小于实际删除条数。为满足 AC-M04-13/38「N 与删除前该类型取值条数一致」，本设计以 **P-03 的返回行数** 作为响应 `deletedCount`（同一事务内的实际删除条数），其与 P-02 计数在无并发时必然相等。
- 处理顺序依赖：P-02 必须先于 P-03（保证「类型不存在」时字典内容不变，AC-M04-15）。
- 出口：成功出口 P-04；失败出口 `M04-E009`、`M04-E008`、`M01-E006`。

#### 4.4 状态、数据与失败处理

- 写入的数据：删除 `component_type` 中 `type = :type` 的全部行；不修改其它行。
- 事务边界：`AppTypeService#deleteType` 标注 `@Transactional`；计数、批量删除与响应装配在同一事务内。
- 提交后可观察结果：该类型不再出现在读取接口的 `types` 中；`typeCount` −1、`valueCount` − N（AC-M04-13、AC-M04-38）；其它类型的取值数量不变。
- 并发冲突：与并发新增同一类型取值竞争时，批量删除可能一并删除刚写入的行（删除范围按类型名匹配，语义上正确）；与并发读取竞争时读取可能看到删除前快照，页面在成功后重新取数保证一致。
- 重复请求的识别与响应：第二次相同请求因 `countByType == 0` 返回 `M04-E008`（类型不存在），与 RC-M04-10 的要求一致；不引入幂等键。
- 超时、中断、部分失败后的状态：批量删除在单事务内，不存在部分删除；提交后响应中断时数据已删除，重试得到 `M04-E008`。
- 资源占用与释放：批量删除的行数受类型规模限制（字典小规模）；无长事务以外的资源；不使用分批提交（RC-M04-08 未要求批次与进度语义）。
- 错误分类与传播边界：`M04-E009`（400）、`M04-E008`（404）、`M01-E006`（503）。

#### 4.5 质量与可验证性

- 安全：无权限校验（需求 1.2 排除范围）；删除范围由类型名精确匹配（归一后精确比较），不做模糊或前缀匹配，避免误删其它类型。
- 性能与容量：`countByType` 与 `deleteByType` 均以 `type` 列为条件；`type` 为既有唯一键 `(type, value)` 的前导列，可复用该索引；批量删除的行数受类型规模限制，无长事务风险（规模见 DQ-M04-17）。
- 日志与诊断：`log.debug` 记录类型名与被删除条数（用于支撑 N 的核对）；失败记录 `traceId`。
- 验收可观察点：提示文案 `类型「X」及其 N 条取值已删除`、左侧列表不再展示该类型、页脚统计变化、`component_type` 与 `specgroup_comptype_rel` 记录集合；对应 V-M04-13、V-M04-15、V-M04-16、V-M04-38、V-M04-39。
- 受控验证支持：类型不存在（构造一个字典中不存在的类型名提交）、未指定（不携带 `type` 参数或传空/仅空白）均可受控触发（AC-M04-15、AC-M04-16）；N 的一致性需在删除前记录该类型取值条数（AC-M04-13/38）。

#### 4.6 复用核对

- 资产标识及版本：`static/js/core/http.js` 的 `withQuery(path, params)`（自动跳过 `null`/`undefined`/空串参数）；`repository/ComponentDefinitionRepository` 的 `@Query` 写法；`BizException` 双参构造。
- 已核对内容：`withQuery` 会跳过空值参数——当类型名为空时，前端将提交不带 `type` 的 `DELETE /api/app-types`，与服务端 C-02 的「未指定」判定天然对齐（无需前端特判）；`@Modifying @Query` 的 JPQL 使用属性路径 `c.type`，不出现裸 `value` 标识符，规避 JPQL 关键字冲突（见 D-M04-11/C-11）。

- 处理方式：复用 `withQuery` 与 `BizException` 范式；新增 `http.del` 与仓储删除方法。
- 影响范围：`http.js` 新增方法不影响既有调用方；仓储为新增类。

| C-01 | 分组口径 | 按 C-04 排序后的取值行列表 | 以 `type` 为分组键；组顺序 = 组内首个记录在排序后列表中的位置 | 不与 `type` 字符串排序混用（不得按类型名拼音或字典序排序） |
| C-02 | 派生统计口径 | 分组结果 | `valueCount(组)` = 组内行数；`typeCount` = 组数；`valueCount(全局)` = 全部行数；三者不落库、不缓存（RC-M04-15） | 统计必须取自同一次读取结果（D-M04-01/C-02） |

#### 4.3 处理逻辑

| 处理项标识 | 条件或触发 | 技术处理 | 状态/数据/外部效果 | 后续或结束 |
|---|---|---|---|---|
| P-01 | 读取装配需要分组 | 接收 D-M04-11/C-02 返回的有序行列表，按 C-01 以 `LinkedHashMap` 分组 | 无 | 交给 D-M04-01/P-05 装配 |
| P-02 | 需要派生统计 | 遍历分组结果累加行数，得到 C-02 的三个值 | 无 | 同上 |
| P-03 | 删除类型或读取需要类型存在性 | 以 `countByType(type)` 与 0 比较（C-03） | 只读 | 交给 D-M04-05/P-02 |
| P-04 | 新增需要排序号 | 读取 `MAX(sort_order)` → 按 C-07 计算目标排序号 | 只读 | 交给 D-M04-02/P-06 |
| P-05 | 预置维度顺序核对 | 以 `AppTypeCatalog.PRESET_TYPE_NAMES` 与列表实际顺序比对（用于验证与自检，不参与运行时排序） | 无 | 结果供 V-M04-11 使用 |

- 关键约束：本构件**不产生排序**（排序由数据库 `ORDER BY` 完成，见 D-M04-11/C-02），只解释排序键与由排序结果导出的分组顺序，避免「数据库排一次、内存再排一次」的双口径。
- 边界：`sort_order` 为 `NULL` 的行参与排序并按最小处理（不排除、不报错）；`sort_order` 的整数溢出按 C-07 处理并不导致异常。
- 出口：返回分组结构、统计值、存在性判定与目标排序号。

#### 4.4 状态、数据与失败处理

- 读写的数据：不直接读写数据库（经 D-M04-11 的方法）；不持有缓存与静态可变状态。
- 事务边界：无自有事务；在调用方事务内执行（读取路径为 `readOnly`）。
- 并发冲突：分组与统计基于单次读取快照，并发写入不影响本次结果的自洽性；排序号赋值在同一事务内读取 `MAX`，并发插入可能产生同排序号——按 C-04 的次级排序键仍有确定顺序（见 D-M04-02/4.4）。
- 重复请求：纯计算 + 只读查询，天然可重复。
- 超时与中断：无外部依赖。
- 错误分类与传播边界：不产生业务错误；`countByType`/`MAX` 的数据库异常由调用方上抛为 `M01-E006`。
- 数据一致性说明：C-02 明确统计为派生值，任何落库的计数都会与 RC-M04-15 冲突，故本构件不提供写入统计的任何路径（结构性保证）。

#### 4.5 质量与可验证性

- 安全：只读，无越权风险；不输出敏感数据。
- 性能与容量：分组与统计为 O(n) 内存遍历；排序由数据库在既有数据规模下完成（DQ-M04-17 记录规模未规定的风险）。
- 日志与诊断：C-07 的溢出分支输出 `warn`（含当前最大值）；其余不输出日志。
- 验收可观察点：读取响应的顺序与统计字段、`sort_order` 序列、左侧计数与页脚文案；对应 V-M04-10、V-M04-11、V-M04-18、V-M04-20、V-M04-21、V-M04-23、V-M04-40。
- 受控验证支持：非连续排序号、同排序号、空排序号三类数据可构造（AC-M04-10、AC-M04-40）；预置顺序核对依赖预置清单（待补充，V-M04-11）。

#### 4.6 复用核对

- 资产标识及版本：无既有排序/聚合构件可复用（`ProjectService` 的读取按 `projectId` 过滤并按阶段顺序由数据行序决定，无同构的聚合展示）；`ComponentDefinitionRepository` 的原生 `@Query` + 行投影接口范式可复用为分组查询的写法（本设计未使用分组查询，见 DD-M04-02）。
- 已核对内容：既有实现中不存在与 `MAX(sort_order)+1` 同构的序号生成逻辑可对标（M02 的阶段顺序由 `sort_order` 字段给定值维护，未做自动追加），故 DD-M04-04 的机制依据为「顺序确定性」而非「与既有实现一致」。
- 与本次需要的差异：本构件为新增（无既有同类构件）。
- 处理方式：不复用；新增独立构件。
- 影响范围：无（不影响既有读取路径的顺序口径）。

#### 4.4 状态、数据与失败处理

- 读写的数据：页面持有**只读的本地快照**（最近一次读取响应）与**临时的编辑态**（行内/新增界面中的未提交输入）；不持久化任何本地状态，不使用 `localStorage`（与 `store.js` 的项目会话态不同，字典不落浏览器存储）。
- 写入条件：仅在服务端返回成功后由读取响应重建快照（C-15）；编辑态输入不视为数据。
- 事务边界：前端无事务；每次写操作是一次独立请求，不存在跨请求的原子性要求（需求未规定批量提交）。
- 并发冲突：同一用户连续操作时，每次写操作完成后立即重新取数，后续操作基于最新快照；行内编辑同一时刻至多一行（C-07）避免并发提交。多用户并发由服务端保证（唯一键 + 计数口径）。
- 重复请求的识别与响应：保存中禁用提交按钮（C-19）减少重复提交；服务端侧重复提交由唯一性判定拒绝（D-M04-02/4.4），前端不引入请求去重标识。
- 超时、中断、部分失败后的状态：请求超时（10 秒，`http.js`）按失败处理（C-10/C-14/C-21），页面不进入不一致状态（不写本地字典）；卸载后的在途响应被 P-13 的代次判断丢弃。
- 资源占用与释放：`destroy()` 释放 DOM、事件监听与定时器（`showToast` 的定时器由 `notice.js` 管理）；不持有长连接。
- 错误分类与传播边界：页面按 `HttpError.message` 展示原因，不解析 `code`（码位用于验证断言与差异化处理）；读取失败与写入失败分别走 C-14 与 C-10/C-17/C-21；不把服务端错误静默吞掉。

#### 4.5 质量与可验证性

- 安全：全部文本经 `textContent` 写入，不使用 `innerHTML` 拼接（沿用 `notice.js`/`ProjectInfo.js` 的既有约定），避免字典内容注入；不展示或记录凭据。
- 性能与容量：单次读取渲染全量字典（规模见 DQ-M04-17）；主从切换为本地重渲染，无网络往返；列表规模增大时不做虚拟滚动（需求未规定规模）。
- 可用性：加载态（`renderLoading`）、空态（C-12/C-13）、失败态（C-14）三态互斥且不白屏；「新增」主操作在空字典下仍可用（RC-M04-17）。
- 日志与诊断：前端不输出 `console` 日志（沿用既有页面约定）；失败原因由界面提示承载，服务端侧以 `traceId` 关联。
- 验收可观察点：页面结构快照（标题、说明、主操作、列清单、占位文案、危险样式）、交互结果（切换、保存、删除、取消）、提示文本与形态；对应 V-M04-21…V-M04-36。
- 受控验证支持：接口不可用可用「停止服务」或拦截请求构造（AC-M04-24）；保存失败可用超限/重复/不存在的记录构造（AC-M04-26、AC-M04-28、AC-M04-29）。

- 组装规则约束：动态片段一律使用**业务值原文**（裁剪后的类型名、类型值、请求记录 ID、实际删除条数），不做转义、截断、加引号以外的加工；文案中的中文引号「」为固定业务值的一部分。

- 出口：返回错误码 + 文案，或返回成功响应字段。

#### 4.4 状态、数据与失败处理

- 读写的数据：无持久数据；`ErrorCode` 为不可变枚举常量。
- 事务边界：文案组装不涉及事务；异常抛出在调用方事务内，`GlobalExceptionHandler` 在事务边界之外完成响应装配。
- 并发冲突：无共享可变状态。
- 重复请求：文案输出幂等。
- 错误分类与传播边界：本单元即错误传播的终点（响应装配），不上抛；`BizException` 不携带堆栈到响应（`ApiError` 只含 `code`/`message`/`timestamp`/`traceId`）。
- 敏感信息：文案不含 SQL、表名、堆栈、内部路径；`X` 为业务标识（记录 ID 或类型名），属用户可见数据，不构成敏感信息泄露。

#### 4.5 质量与可验证性

- 安全：错误响应不泄露实现细节（既有 `GlobalExceptionHandler` 已保证未预期异常统一为 `M01-E006` + `traceId`）；前端以 `textContent` 渲染文案，避免注入。
- 性能与容量：无影响。
- 日志与诊断：错误码与 `traceId` 是验收断言的观察入口；日志中记录 `code` 与 `traceId`，不重复记录完整文案。
- 验收可观察点：HTTP 状态、响应 `code` 与 `message`、页面提示文本与形态；对应 V-M04-01…V-M04-09、V-M04-14、V-M04-15、V-M04-16、V-M04-24、V-M04-26、V-M04-28、V-M04-29、V-M04-34、V-M04-36。
- 受控验证支持：全部文案可由构造输入精确触发；`M04-E006` 的库级冲突分支需专门构造（V-M04-42）。

#### 4.6 复用核对

- 资产标识及版本：`support/ErrorCode`（既有 `M01_E001`…`M01_E007`、`M02_E001`…`M02_E003`，各含 `code`/`httpStatus`/`message`）；`support/BizException`（单参与双参构造）；`support/GlobalExceptionHandler`（`@RestControllerAdvice`：`BizException` → 对应码位；绑定失败 → `M01-E001` 400；未预期异常 → `M01-E006` 503 + `traceId`）；`support/ApiError`（`record ApiError(String code, String message, Instant timestamp, String traceId)`）；`static/js/core/notice.js` 的 `showToast`/`renderFailure`。
- 已核对内容：`ErrorCode` 的 javadoc 明确「编码与 HTTP 状态的对应关系是接口契约的一部分，前端按 `code` 做差异化提示，不得随意调整。M02 只新增码位，既有码位与 HTTP 状态不变」——本设计的扩展方式（只新增 `M04-E00x`，不改既有项）与之一致；`BizException` 双参构造支持动态文案，`ApiError.of(String, String, String)` 支持任意文案，均无需改造；`showToast` 的 `type` 支持 `'warn'`/`'error'` 样式，满足 C-16。
- 与本次需要的差异：`ErrorCode` 当前无任何 M04 码位（已核对）；本模块需要 9 个新码位（C-01…C-09）与 3 条超限文案（需求未给出，DD-M04-05）。
- 处理方式：扩展式修改。在 `ErrorCode` 中新增 9 个枚举项，每项 javadoc 标注关联条款（RC 编号）与设计位置，沿用 M02 的注释风格；不修改 `GlobalExceptionHandler`、`BizException`、`ApiError`。
- 影响范围：新增码位对既有前端分支无影响（前端按 `code` 分支时未知码位退化为通用提示）；`ErrorCode` 枚举的既有项、顺序与 HTTP 状态不变，M01/M02 的既有验证结论继续有效。

- 数据来源：单一表 `component_type`；无关联查询、无 JOIN（C-12）。
- 顺序依赖：判重与存在性判定必须先于写入/删除，且与写入处于同一事务（D-M04-02/4.4、D-M04-03/4.4）。
- 出口：返回实体、集合、计数或受影响行数；数据库异常上抛（由 `GlobalExceptionHandler` 映射）。

#### 4.4 状态、数据与失败处理

- 读写的数据：`component_type` 的全部六个列；不读写其它表（C-12）。
- 事务边界：由 `AppTypeService` 控制；仓储方法参与调用方事务；`@Modifying` 查询需配合调用方事务（`@Transactional`）使用，否则抛出 `TransactionRequiredException`——该约束在实现时以服务层事务标注满足。
- 并发冲突的检测与处理：唯一键 `(type, value)` 是并发重复写入的检测机制，冲突以 `DataIntegrityViolationException` 暴露（C-08），由服务层映射为 `M04-E006`；不使用悲观锁与 `SELECT ... FOR UPDATE`。
- 重复请求：无幂等键（RC-M04-14）；读操作天然幂等，写操作的重复由唯一键与存在性判定约束。
- 超时、中断、部分失败：单条语句或单事务批量语句，不存在部分完成；连接由连接池管理并释放。
- 外部副作用与本地状态一致性：无外部系统；表结构为外部 DDL 维护，本构件只读写数据（`ddl-auto: none`），不触发 DDL。
- 错误分类与传播边界：数据访问异常（连接失败、约束冲突、SQL 异常）抛出为 Spring 的 `DataAccessException` 家族；`DataIntegrityViolationException` 由服务层单独捕获并映射为业务码（DD-M04-06），其余交由 `GlobalExceptionHandler` 统一为 `M01-E006`。

#### 4.5 质量与可验证性

- 安全：全部查询使用参数绑定（派生方法、`@Query` 命名参数），无字符串拼接 SQL；`deleteByType` 的类型名来自归一后的查询参数，不存在注入面。

#### 4.3 处理逻辑

本单元为声明式配置单元，不展开处理表（模板允许）：常量为 `static final`（服务端）与模块级 `const`（前端），无计算、无副作用、无 I/O；加载方式为类加载/模块导入时初始化；变更生效机制为「随代码发布生效」，不提供运行时配置与热更新（需求未要求可配置，DEF-M04-13 明确文案为固定业务值而非可配置参数）。

#### 4.4 状态、数据与失败处理

- 读写的数据：无持久数据；常量为不可变值。
- 事务边界与并发：无。
- 失败处理：无失败路径（常量缺失属编译期或加载期错误，不在运行时降级）；前端文案常量缺失会在页面渲染时以 `undefined` 暴露，由 V-M04-33/34/35 的结构断言覆盖。
- 敏感信息：常量不含敏感信息。

#### 4.5 质量与可验证性

- 验收可观察点：页面标题、说明、占位、页脚文案的实际渲染文本（逐字比对）；超限判定使用的上限值（64/255）；预置维度顺序核对结果；对应 V-M04-04、V-M04-11、V-M04-33、V-M04-34、V-M04-35、V-M04-36。
- 受控验证支持：文案逐字比对可用页面结构快照；上限值可用 64/65 字符构造；预置清单比对依赖清单补充（V-M04-11 待补充）。

#### 4.6 复用核对

- 资产标识及版本：`static/js/pages/ProjectInfo.js` 的模块级常量组织（`NAME_MAX_LENGTH = 128`，注释「前端校验为体验优化，不替代服务端校验（RC-M02-01）」）；`support/ErrorCode` 的枚举常量组织方式（与常量清单同类的「单一定值来源」做法）。
- 已核对内容：既有前端页面以模块级 `const` 承载文案与上限，本设计沿用同一组织方式；M02 的 128 上限同时存在于前端常量与服务端 `ErrorCode` 文案中（两处），本设计为避免同类重复，将上限集中到 `AppTypeCatalog`（服务端）与页面顶部常量（前端），并在 C-01 要求两者取值一致。
- 与本次需要的差异：既有实现无独立的服务端常量类（上限仅出现在 `ErrorCode` 文案与前端常量中），本模块新增 `AppTypeCatalog` 以承载上限与预置清单。
- 处理方式：新增（服务端常量类）+ 复用组织方式（前端常量）。
- 影响范围：无（新增类，不被既有代码引用）。
