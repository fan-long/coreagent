# 通用结构化需求

> Agent Spec 模板 · 阶段：需求分析

# <需求标识> <需求名称> —— 结构化需求规格

> 本模板用于将外部需求文档、业务模型及关联规范转换为统一、可追踪、可验证的需求规格。
>
> 需求条款是统一追踪单元；共享定义提供语义；CAP 或业务步骤组织条款；验收检查点定义验证义务。
>
> 本文档不替代技术设计、实施任务或测试报告，也不因填写完成而证明实现正确。

## 填写约定

### A. 转换原则

1. 提取范围包括正文、表格、图示、附件和外部引用，不限于标题含“规则”或“约束”的章节。
2. 所有系统必须满足的要求均转换为需求条款；背景说明、术语和事实定义不强行转换为条款。
3. 同一要求只保留一个权威表达，其他位置通过编号引用；不得在条款、CAP、步骤和验收点中维护不同口径。
4. 保留原文的适用范围、责任边界、条件、单位、时间口径、义务强度和例外。
5. 不将“仅当”扩展为“当且仅当”，不把必要条件自动解释为充分条件。
6. 不自行补充默认值、回退、重试、事务、补偿、权限、并发或重复处理政策。
7. 已明确的业务或技术约束必须保留；原文未规定的技术实现方式不得作为需求补入。
8. 同义要求可合并并保留全部来源；冲突要求登记待决事项，不按文档顺序或日期自行裁决。
9. “已明确”必须有依据，不要求逐条人工确认；AI 推测不能作为依据。分析归纳不得新增业务政策。
10. 表格中的占位行用于复制填写，不代表实际业务要求；生成结果应删除占位提示和未选择的组织模式章节。

### B. 编号与引用

* SRC：来源资料。
* DEF：共享业务定义。
* RC：需求条款。
* CAP：能力，仅用于能力型需求。
* ST：业务步骤，仅用于业务建模型需求。
* AC：验收检查点。
* Q：待决事项。

编号在本需求内唯一，对外引用使用“需求标识＋条目标识＋版本”。

编号不随排序、章节位置或组织分组变化而重排。已有稳定编号可以保留，不为采用本模板而强制重新编号。

### C. 未明确信息的处理

* 已明确：有可定位依据，相关语义足以支持设计和验证。
* 待澄清：存在影响理解或实施的信息缺失、歧义或未解析引用。
* 冲突：存在不能同时成立且尚未确定优先关系的要求。
* 不适用：有明确理由证明该内容不属于当前需求，不得用于代替缺失信息。

缺失字段不能默认表示“无约束”。有影响的缺失必须关联 Q。

## 2\. 共享业务定义

本节统一解释条款使用的概念、结构和取值依据。

系统必须遵守的约束由 RC 承载，可以引用完整定义或其中的字段、行项，不必重复抄写。

### 2.1 概念、对象与数据结构

|定义编号|类别|名称|业务含义或结构|来源|
|-|-|-|-|-|
|DEF-001|<概念 / 对象 / 属性 / 关系 / 状态 / 文件结构>|<名称>|<准确含义、结构或引用位置>|<SRC 及位置>|

按实际内容展开：

* 对象：标识方式、归属范围、相关对象及关系。
* 属性：数据类型、单位、精度、枚举含义及空值含义。
* 状态：每个状态的业务含义；转换约束由 RC 承载。
* 文件或集合：记录粒度、字段结构、关联标识。
* 统计或派生数据：基础数据、统计集合、排除项及口径；计算要求引用 RC。

结构复杂时可附字段表，使用 DEF 编号及字段标识定位。不得把强制性约束仅写在附表中而不关联 RC。

### 2.2 参数与外部契约

|定义编号|名称与类别|权威来源|适用范围与使用含义|缺失或待决项|
|-|-|-|-|-|
|DEF-002|<参数 / 接口 / 事件 / 核算规范 / 质量基线>|<版本、参数键、接口编码或具体章节>|<何时使用、影响什么>|<无，或 Q 编号>|

填写要求：

* 区分固定业务值、可配置参数和示例值，不把当前配置固化为普遍规则。
* 参数的选择条件、有效期、优先级或缺失处理影响业务时，必须明确或登记 Q。
* 外部接口必须定位到实际使用的输入、输出、错误或事件契约。
* “参见某文档”不代表契约已解析。
* 未经依据，不在多个来源之间建立隐式回退关系。

## 3\. 可验证需求条款

### 3.1 条款定义

需求条款是在明确的适用范围和条件下，对目标系统提出的一项可独立判断是否满足的要求。

一条条款可以包含同一决策的多个分支，但分支须可定位并分别验证。

能够分别违反、分别修改的要求通常应拆分；不得仅按原文句号机械拆分，也不得把整个功能作为一条无法检查的要求。

### 3.2 条款类型

|类型|表达内容|重点检查|
|-|-|-|
|业务规则|许可、禁止、决策、计算及业务不变量|条件、结论、计算口径、例外及优先级|
|功能行为|必须执行的动作、状态变化和业务效果|触发、动作、完成条件、成功及失败结果|
|数据要求|数据结构、含义、关系、记录与保留要求|对象范围、数据契约、关联及有效性|
|交互契约|人机或系统间的信息交换与协作|输入、输出、错误、关联标识及交互时序|
|质量约束|规定条件下的质量指标与保障要求|环境、负载、指标、阈值及测量口径|

每条选择一个主类型；不因同一要求涉及多个方面而重复登记。

### 3.3 条款清单

|条款编号|类型|适用范围、条件与责任边界|规范性要求|边界、例外与依赖|来源|明确性|
|-|-|-|-|-|-|-|
|RC-001|<类型>|<对象、角色、状态、输入或触发；持续约束注明适用期间>|<必须满足的行为、结果、约束或指标>|<具体说明，或 DEF、RC、Q 引用>|<SRC 及具体位置>|<已明确 / 待澄清 / 冲突>|

### 3.4 表达要求

* 可以使用“当……时，系统必须……”等结构化句式，但不强制将持续不变量、数据结构和质量指标改写为事件触发形式。
* 不使用“正常处理”“保证正确”“符合规定”等无明确判定依据的独立表述。
* 保留原文的强制、建议和可选含义；“允许办理”通常是能力或许可要求，不能直接解释为可不实现。
* 决策表、公式或结构表可作为条款附表，使用“RC 编号＋分支/行项编号”定位。
* 强制顺序、例外优先级、跨功能一致性均须有 RC 承载，不能只存在于流程图或文字说明中。
* 全局条款可以直接作用于整个需求范围，无须强行绑定单个 CAP 或 ST。
* 新增政策、缺失条件和未确认解释必须进入 Q，不能用分析归纳替代业务依据。

按需求特征检查：

* 计算：公式、参数、单位、精度、舍入及有效范围。
* 时间：时间来源、起算点、边界包含关系、日历口径及到期结果。
* 状态：原状态、事件、允许条件、目标状态及禁止转换。
* 异步：受理、业务完成、结果关联和结果获取方式。
* 批量：单条、文件、批次及汇总结果，部分失败与整批失败的边界。
* 一致性：必须共同成立的结果、允许的中间状态及失败后的业务状态。
* 资源：占用、释放、消耗等业务要求及其成立条件。
* 质量：适用范围、运行环境、负载、统计窗口、指标和阈值。

> 本清单用于发现缺失，不用于自动补充业务政策。例如发现未规定重复提交的处理时，应登记 Q，而不是默认要求幂等。

## 4\. 需求组织

根据第 1 节选择，仅保留 4A 或 4B。生成结果不得同时存在两套组织表，也不得互相创建映射来重复表达同一业务。

组织表只表达业务结构与摘要，具体要求以 RC 为准。

### 4A. CAP 组织方式

仅组织模式为 CAP 时保留本节。

CAP 表示系统提供的一项具有业务目的、边界及可观察结果的能力，不等同于页面、接口或程序方法。

|能力编号|名称与业务目的|使用者与触发|输入及边界|对外结果与完成条件|适用条款|来源或归纳依据|
|-|-|-|-|-|-|-|
|CAP-001|<名称与目的>|<角色、系统、事件或调度>|<输入或 DEF 引用、责任边界>|<明确受理与完成的区别>|<RC 编号>|<SRC，或所依据的条款>|

* 原文已有明确能力边界时优先保留。
* 可以归纳能力名称与分组，但不得新增要求。
* 一个 CAP 可以引用多条 RC，公共 RC 可以适用于多个 CAP。
* 只描述业务能力，不在此拆分代码执行任务。

### 4B. 业务步骤组织方式

仅组织模式为 ST 时保留本节。

业务步骤是业务模型中的活动，描述谁在什么业务条件下做什么、产生什么业务结果，不是技术执行步骤。

* 业务模型及流程来源：<SRC 与模型/流程标识>
* 业务目标：<业务过程要实现的结果>
* 起始条件：<业务事件及前置状态>
* 结束条件：<成功、失败或其他明确终态>
* 参与方与责任边界：<本系统、人员及外部系统的责任>

|步骤编号|所属业务流程|执行主体|业务活动|进入条件|业务结果|后继关系与条件|适用条款及来源|
|-|-|-|-|-|-|-|-|
|ST-001|<源模型流程标识或名称>|<人、组织或系统>|<活动摘要>|<事件、状态或前序结果>|<产出、状态或外部效果>|<后继 ST、分支、并行、等待或结束>|<RC 与 SRC 引用>|

* 保留源业务模型的步骤身份与业务关系，不额外建立 CAP。
* 步骤编号或文档排列顺序不代表执行顺序，顺序以明确关系为准。
* 人工和外部系统活动可保留为流程上下文，须标明是否属于本系统实施范围。
* 强制业务顺序和业务结果须引用对应 RC。
* 未明确的分支、并发、撤销或恢复关系登记 Q，不补造完整流程。
* 流程图可辅助展示，但须复用同一套步骤编号和条款。
* 原模型存在缺陷时记录问题，不在转换中无痕修正。

## 5\. 适用范围与跨条款关系

本节表达无法仅靠分组保留的组合语义，不重复组织表已经明确的关系。

|关系类型|来源条目|目标条目或范围|适用条件与关系含义|依据|
|-|-|-|-|-|
|<适用于 / 依赖 / 例外于 / 优先于 / 必须共同成立>|<RC 编号>|<RC、DEF、所选组织单元或整个需求范围>|<明确关系>|<承载该关系的 RC 或具体来源>|

* 强制性关系须有 RC 承载。
* 公共条款定义一次，通过适用关系复用。
* 不得用推测的优先级掩盖冲突。
* 组织调整不改变条款身份。
* 无额外关系时可注明，不为填表建立无业务意义的关联。

## 6\. 验收检查点

AC 是验证条款满足或违反所需的检查义务，不是测试案例执行记录。

### 6.1 检查点清单

|检查点编号|条款及分支引用|验证形式|条件与数据范围|操作、事件或观察过程|预期断言|判定依据与观察入口|
|-|-|-|-|-|-|-|
|AC-001|<一个或多个 RC 及分支>|<场景 / 性质 / 测量 / 静态契约检查>|<初始状态、输入域、环境或对象集合>|<可执行或可检查的过程>|<可判断满足或违反的结果>|<期望依据及接口、数据、事件、界面或检测方式>|

### 6.2 验证形式说明

* 场景验证：给定具体条件、操作或事件，检查预期结果，适合正常、异常、边界和状态分支。
* 性质验证：在明确输入域、状态域或操作序列中检查应持续成立的关系，适合不变量、守恒关系、计算性质等。
* 测量验证：在规定环境、负载和时间窗口中测量指标，适合性能、容量、可用性等要求。
* 静态契约检查：检查结构、声明、接口或其他可静态判定的约束。

不得为使用性质测试而增加原需求没有规定的不变量、幂等或可逆性要求。

### 6.3 覆盖要求

* 每条已明确 RC 均须有对应检查点；必要分支、边界和例外分别覆盖。
* 一条 RC 可有多个 AC，一个联合 AC 也可验证多条相关 RC。
* 预期结果来自需求、权威契约或可核验推导，不从生成代码反推。
* 除接口响应外，还应检查适用的状态、数据记录、业务资源和外部效果。
* 异步受理成功不等于业务完成，须分别检查适用的阶段性结果和最终结果。
* 批量需求分别检查单条、文件、批次及汇总结果。
* 跨能力或跨步骤要求需要联合验证，不能仅靠各局部独立成功证明。
* 性质验证必须明确输入域、前置条件及例外；随机测试通过不等于穷尽证明。
* 缺少可判定预期或观察依据时登记 Q，不编造精确断言。

### 6.4 下游追踪约定

* 设计、实现单元、测试和问题关联 RC，测试同时关联 AC。
* 条款与实现允许多对多关联，不要求每条条款生成一个规则函数或代码方法。
* 运行证据在下游记录，至少定位到规格版本、实现版本、环境和执行结果。
* 分别统计来源处置、条款就绪、设计实现关联、检查点覆盖及执行通过情况。
* 有关联不等于已覆盖，有覆盖不等于执行通过，执行通过不自动证明源需求完整。
* 本文档不填写未经执行验证的“已实现”或“测试通过”。

## 7\. 待决事项与就绪判断

### 7.1 待决事项

|问题编号|类型|问题及原文依据|影响范围|是否阻断及原因|所需补充或决策|结论与依据|
|-|-|-|-|-|-|-|
|Q-001|<缺失 / 歧义 / 冲突 / 引用未解析>|<具体问题及 SRC 位置>|<相关条目或尚未提取的源要求>|<是/否及原因>|<需要明确的信息>|<未解决，或有依据的结论>|

* 尚未形成 RC 的问题直接关联原文。

* 非阻断项须说明为什么不影响当前实施范围。
* 结论形成后更新受影响的条款、组织关系和验收点，保留处置依据。

## 8\. 相对基线的变更记录

首次建立需求时注明“首次建立，无对比基线”，不填写虚构差异。

发生变更时，第 3 节表达本次范围内的完整目标要求，本节表达相对指定基线的差异。候选规格不能自动覆盖已生效基线。

|变更类型|基线条目及版本|目标条目及版本|变化内容与依据|受影响范围|需重新评估或验证的内容|
|-|-|-|-|-|-|
|<新增 / 修改 / 删除 / 拆分 / 合并>|<旧 RC 或相关定义；新增填无>|<新 RC 或相关定义；删除注明不再适用>|<差异及 SRC、Q 结论或变更依据>|<定义、条款、组织单元、AC 及下游关联>|<设计、实现、检查点或已有证据>|

变更处理要求：

* 同一要求的修订通常保留标识并更新版本。
* 拆分、合并时记录旧条目与新条目的对应关系，不丢失来源和历史。
* 删除表示在目标范围内不再适用，不销毁历史条款与验证记录。
* 共享定义、参数口径或适用范围变化时，评估引用它们的条款，即使条款正文未改动。
* 相关要求或实现变化后，旧证据必须重新评估适用性；未完成评估不得直接继承“通过”结论。
* 规格生效、实施完成和验证通过分别由对应流程及证据判定，不能因文
